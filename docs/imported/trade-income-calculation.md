# EU4 Trade Income: Calculation Mechanics & Optimal Allocation Algorithm

## 0. Scope & Assumptions

This document models the core trade mechanics needed to compute a country's trade
income and to find the optimal merchant/ship allocation. It deliberately
**excludes** edge-case mechanics that add complexity without changing the
algorithmic approach:

- Privateers, piracy, and node "pirate power"
- Trade leagues, embargoes, transfer-trade-power casus belli effects
- Trade company investments / province-level trade buildings beyond their
  aggregate effect on local value and power (these are captured as inputs,
  not modeled internally)
- Estate/parliament trade bonuses (treated as static modifiers, folded into inputs)
- Missions/events granting one-off trade power (folded into inputs as bonuses)

These are all **input modifiers**, not structural mechanics — they change the
numbers fed into the model but not the shape of the computation.

---

## 1. Data Model

### 1.1 Trade Node Graph
The world's trade nodes form a **directed acyclic graph (DAG)**:

- `Node`: a trade node (e.g., "English Channel", "Genoa")
- `Edge(upstream → downstream)`: a fixed trade route; some nodes split
  outgoing value across multiple downstream edges by a fixed base
  percentage (defined by the game's static node data)
- `end_node`: a node with no outgoing edges (value collected there cannot
  propagate further)

Only nodes reachable from a node where the country has **trade range**
(via owned provinces, colonial range, or merchant range extension) are
"active/in-range" and relevant to this player.

### 1.2 Per-Node Inputs (parsed from the save file)
| Field | Description |
|---|---|
| `local_value` | Trade value generated by goods produced in this node (goods produced × current price, summed across provinces in the node) |
| `total_power` | Sum of trade power of **all** countries present in the node |
| `your_power` | This country's trade power in the node (before ship/merchant changes being tested) |
| `outgoing_splits` | List of `(downstream_node, base_fraction)` — how local+incoming value is distributed downstream by default |
| `has_merchant_slot_available` | Whether a merchant *could* be assigned here (i.e., it's in range) |
| `node_modifiers` | Node-specific multipliers (e.g., trade value modifiers, steering caps) |

## 2. Trade Power Calculation

Trade power in a node is the sum of:

```
your_power(node) =
      power_from_owned_provinces_in_node          (base provincial trade power,
                                                     scaled by production/trade buildings)
    + power_projected_from_adjacent_nodes_in_range  (provinces outside the node projecting
                                                     power into it, reduced by distance/range)
    + light_ship_trade_power(node)                  (sum of light ships stationed there;
                                                     each ship contributes a fixed base amount,
                                                     modified by naval/trade tech and ideas)
    + merchant_trade_power_bonus(node)              (flat bonus if a merchant occupies
                                                     this node, modified by ideas/policies)
    × global_trade_power_modifiers                  (national ideas, policies, government
                                                     reforms — multiplicative)
```

**Your power share:**
```
share(node) = your_power(node) / total_power(node)
```
This share determines both how much value you can collect **and** how much
influence you have over steering direction (steering effectiveness is also
gated by having a merchant present).

---

## 3. Trade Value Propagation

For each node, in **topological order from source nodes toward end nodes**:

```
incoming_value(node) = Σ over upstream edges:
    value(upstream) × outgoing_fraction(upstream → node)
```

```
total_value(node) = local_value(node) + incoming_value(node)
```

`outgoing_fraction` starts at the node's static base split, but is modified
by **steering**:

```
outgoing_fraction(node → target) =
    base_fraction(node → target) + steering_bonus(node, target)
```

- `steering_bonus` is nonzero only if a country has placed a merchant on a
  **"steer trade"** mission in `node` targeting `target`. Typical effect:
  a flat percentage-point boost to that edge's share of outgoing value
  (magnitude depends on the steering country's power share in the node,
  merchant steering modifiers, and idea bonuses).
- Multiple countries can steer the same node toward different targets;
  their bonuses are additive up to the node's cap (remaining local value
  distributes across edges proportionally to the adjusted fractions,
  renormalized to sum to 100%).

---

## 4. Collecting Income

A country collects ducats from a node in one of two ways:

1. **No merchant present / merchant on "collect":**
   Ducats gained = `total_value(node) × share(node)`, subject to
   national trade efficiency multiplier.
2. **Merchant on "steer":**
   The country **forgoes collection in this node** — instead its share of
   value is redirected downstream (via the steering bonus above), aiming
   to capture more value later where its power share or the endnode
   conversion is more favorable.

```
ducats_from_node(node) =
    IF acting_as_collector(node):
        total_value(node) × share(node) × trade_efficiency
    ELSE:
        0   (value passed downstream instead, captured elsewhere in the DAG)
```

**Total trade income** = sum of `ducats_from_node(node)` across every node
where the country collects (usually just its home node plus any node it
actively holds a "collect" merchant in — power share alone, without
collecting, does not by itself generate ducats **except** in the country's
home node, which always auto-collects).

---

## 5. Effect of Specific Actions (what the calculator toggles)

| Action | Mechanical effect |
|---|---|
| **Add a light ship (e.g., Frigate) to node X** | `+ship_trade_power` to `your_power(X)`, raising `share(X)` and every downstream node's incoming value it steers into |
| **Place merchant, mission = Collect** | Small flat power bonus in that node + enables that node to be an explicit collection point |
| **Place merchant, mission = Steer → target** | Removes this node's collection for you; adds `steering_bonus` to the `(node → target)` edge, increasing `total_value(target)` |
| **Move merchant elsewhere** | Reallocates the above effects; every downstream node's value must be recomputed |

Because value propagates downstream, **every change to power or steering in
an upstream node ripples through all descendant nodes** — the whole DAG
must be recomputed on any change, not just the modified node (though only
descendants of the changed node actually need recomputation).

## 6. Optimization: Finding the Optimal Allocation

### 6.1 Problem statement
Given:
- A DAG of `N` in-range nodes
- A pool of `M` merchants (each assignable to one in-range node, action = Collect or Steer→target)
- A pool of `S` light ships (each assignable to one in-range node)

Find the assignment that **maximizes total ducats collected**.

### 6.2 Why this is tractable (not brute-force over all assignments)

Two structural properties make this fast:

1. **The DAG has no cycles** → value only flows one direction, so the
   optimal collect/steer choice can be computed with a single backward
   pass (dynamic programming), not by trying combinations.
2. **Power share is concave in your own power** (`your_power / (your_power + rest)`
   flattens as you add more power) → for a *fixed* set of collect/steer
   decisions, optimal ship allocation is a classic **separable concave
   resource allocation problem**, solvable optimally by a **greedy
   marginal-gain algorithm** (exchange-argument optimal).

The only real complexity is that ship allocation and collect/steer
decisions are **coupled** (more power in a node can flip its best decision).
Section 6.5 handles that coupling cheaply.

### 6.3 Step 1 — Downstream value multiplier (DP over the DAG)

Process nodes in reverse topological order (end nodes first). Define:

```
best_multiplier(node) =
    max(
        share(node),                                     // collect here
        max over outgoing edges e = (node → target):
            steering_efficiency(e) × best_multiplier(target)   // steer instead
    )
```

`best_multiplier(node)` represents: "for one unit of value sitting in this
node, what is the best eventual ducat yield, whether collected now or
routed onward?" This is computed once, **O(N)** total.

### 6.4 Step 2 — Greedy ship allocation (fixed decisions)

For the collect/steer decisions fixed by Step 1:

1. For each node, compute the **marginal ducat gain** of adding one more
   ship there: `Δducats = f(your_power + Δp) − f(your_power)`, where `f`
   folds in `best_multiplier` for that node.
2. Push all nodes into a max-heap keyed by marginal gain.
3. Pop the top node, assign one ship, recompute its (now slightly smaller,
   due to concavity) marginal gain, push it back.
4. Repeat until all `S` ships are assigned.

This is **O(S log N)** and is provably optimal *for the fixed decision set*
(standard result for allocating discrete units across concave, separable
reward functions).

### 6.5 Step 3 — Reconciling coupling (decisions ↔ ship allocation)

1. Run Step 3 (DP) → Step 4 (greedy ships) once.
2. Recompute Step 3's DP using the *updated* power values from Step 4
   (extra ships may change which nodes should flip collect ↔ steer).
3. Repeat 1–2 until the decision set stops changing (empirically converges
   in 2–3 iterations).
4. **Exactness pass:** flag any node where `collect` vs `steer` payoffs are
   within a small epsilon (a genuine toss-up). Brute-force enumerate only
   the combinations of these flagged nodes (typically far fewer than N),
   rerunning Steps 3–4 for each combination, and keep the best result. This
   guarantees a true (not just heuristic) optimum for the flagged set while
   keeping the search space small.

### 6.6 Complexity & runtime estimate

| Step | Complexity | Typical scale | Est. time |
|---|---|---|---|
| DAG DP | O(N) | N ≈ 20–40 nodes | <1 ms |
| Greedy ship allocation | O(S log N) | S ≈ 20–80 ships | <5 ms |
| Iterate to convergence | ×2–3 | — | <20 ms |
| Exactness brute-force on close ties | O(2^k × N), k = # flagged nodes | k typically ≤ 8–10 | <50–200 ms |

**Total: well under 1 second**, comfortably inside a "few seconds" budget
even with UI re-render and re-fetch overhead. A true worst-case pathological
save (every node a toss-up) would still resolve in low single-digit seconds
before the 2^k term becomes a real concern — at which point capping `k`
(e.g., only brute-force the 12 closest ties, heuristically fix the rest) is
a safe, negligible-error fallback.

### 6.7 Output of the optimizer
For each in-range node: `{ merchant_assigned: bool, action: collect|steer, steer_target?: node_id, ships_assigned: int }`, plus the resulting `total_ducats` — this is exactly the shape needed to render the "Optimal" preset in the What-If calculator (see the visualization doc).
